# Windows 0.5.16 验证记录与已知限制

日期：2026-10-29。代码基线为已 fetch 的 origin/main `87db723aef74aa2bb08dbeaab6cf8a6e6a870928`。
本次版本发布 ML307 复位后的身份核验修正及 ESP32 完整写入后的只读校验恢复。持续失效的 USB 连接尚未验证可自动恢复，不把本版本描述为全部烧录问题已解决。

## 追加实机复查

四块已经写过固件的测试板，追加五轮共 20 次双芯任务。前三轮使用实际安装的 EXE，后二轮在同一进程内使用与 GUI 相同的账号快照及 Batch 生命周期。结果为 19 次双芯成功、1 次 ESP32 失败；ML307 20 次全部写入、授权及启动身份核验通过。不能将早前两轮通过外推为工厂稳定性保证。

唯一失败发生在 ESP32 发送完整 16 MB 后、MD5 校验期间：Windows 返回 `Cannot configure port / PermissionError(13, ..., None, 22)`。设备仍被系统列为 COM 口，随后打开却返回文件不存在。ML307 启动核验已在该错误约 19 秒前完成，当前证据不足以归因为双芯复位竞态、授权权限或网络。

本轮 54 次官方接口请求均直连，无网络失败、无重试。五份 CSV 均准确保存四条任务，和最终记录字节一致；失败行仍为失败，没有修改历史结果。结束后没有遗留烧录进程、工作线程或端口锁。

## 软件恢复实验及断电对照

普通串口重连、定向重启 ESP32 串口接口、定向重启 ESP32 物理 USB 设备以及只复位 ESP32 所在的 USB 子端口，均未证明能够恢复该故障。部分操作后暂时可以打开或读到 MAC，但后续校验再次失败。没有复位共享 Hub、没有修改系统驱动或全局电源策略。

未将这些无效的 PnP 恢复操作纳入产品自动流程。它们的 Windows 诊断脚本和原始日志仅留在测试机，不构成已修复的证据。

用户随后重新插拔了全部四块板。只读取回每块完整 16 MB 后逐分区对照：四块的 bootloader、分区表、app0、app1、SPIFFS、coredump 都与原批次镜像一致；差异仅在 NVS 和 otadata 的两个扇区。包括原失败板，均没有发现固件本体写坏。此时设备已启动过，整盘与出厂镜像的 MD5 不一致不能作为历史烧录损坏证据；烧录流程仍要求首次启动前完整 MD5 一致，判定未放宽。

此对照没有重新擦写、没有额外领取授权。检查后四块 ESP32 已复位运行，四个 ESP32 端口和四个 ML307 运行口均在。断电后恢复证明 USB 状态已经恢复，不证明引发失效的根因已经修复。

## 源码修正及软件验证

增加“完整写入后的只读校验恢复”：只有官方 esptool 明确报告地址 0、完整 16 MB 已写完并进入 MD5，且后续为传输错误，才重新确认原板 MAC 并只读复核完整 Flash。不会重发写入或领取授权。

部分写入、地址/长度不符、换板、实际 MD5 不一致、快照改变、取消以及子进程占用未释放均不能跳过。恢复仍失败时，明确显示数据已发送但校验未通过，不能显示成功。

Windows 回归 **298 项通过**；源码编译检查通过。覆盖 20 批次及 80 个中断连接代次的调度/端口释放/CSV 软件测试。编译前移除了已核对文件头的 AppleDouble 传输元数据；不是业务代码错误，不在已交付包中。

这些软件测试验证恢复分支和失败边界，**没有证明能自动修复本次持续失效的 USB 连接**。该实机恢复缺口仍存在，在 README 和公开发布说明中明确保留。
